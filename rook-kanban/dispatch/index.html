Rook / KanbanAgent 交付设计

rook-chat 拉取与派发

用同一条已确认的 Task「修复重试路径漏发」演示三种派发方式。开发 Agent 都通过 rook-chat 读取 Task。区别在于谁选择执行者、谁触发开工，以及开发环境离线时谁负责处理。

三种派发方式怎么选

方案选择 Task 和开发环境离线和失败最低实现依赖
一 · RD 手动派发RD 在自己的开发环境打开 Agent，把指定 Task ID 交给它。Task 留在「待处理」，等 RD 有空接单。rook-chat 按 ID 读取授权 Task；沿用 Kanban 的接单操作。
二 · 开发环境自动领取RD 预先授权一个开发环境。该环境空闲时，主动领取已分配给 RD 且允许自动开发的 Task。开发环境恢复空闲后再拉取。多个环境抢到同一条时，Rook 只给一个环境领取权。开发环境的领取进程、可领取列表、带版本校验的领取和接单确认。
三 · Rook 主动派发Rook 根据 Project 路由选择已登记的开发环境，并向它投递 Task ID 和派发标识。Rook 记录等待接单、超时和失败。重投使用同一派发标识，到期后交人工处理。Project 路由、接收端登记、持久化派发记录和接单确认。

推荐先做方案一

先验证 RD 只拿到 Task ID，能否用 rook-chat 读到足够开工的信息，并把 MR 和验证结果提交给验收人。三个方案共用这个读取契约，自动化只改变 Task ID 怎么到达开发 Agent。

如果主要想省掉 RD 每次复制 Task ID，且开发环境有空时可以自己接单，选方案二。如果团队要按 Project 把需求发到指定的开发环境，并集中查询每次派发结果，选方案三。

共用的读取和状态规则

  • Task 包含目标、范围、复现信息、验收条件、所属 Project 和当前 revision。来源 Chat 仍按原权限访问。
  • rook-chat 使用当前授权身份读取 Task。读取只返回内容。接单确认让 Task 进入「处理中」。自动派发还需提前授权 Project、开发环境和可自动领取的任务范围。
  • 方案二由 Rook 原子确认单一领取者。方案三由接收端按派发标识去重。接单状态不明时先核对是否已启动，再决定是否释放领取或重投。
  • 首期 RD 从卡片提交 MR 和验证结果。验收人通过后，Task 进入「已完成」。

现有 rook-chat 支持 Chat 和 Run。现有 Kanban 已有 Task 详情和带 revision 的状态更新。本原型的 Task 拉取和自动派发是待实现设计。
