01 · 目标与非目标

MUST跨 Worker 原生恢复

Worker B 不依赖 Worker A 的本地磁盘，从 MySQL 找到已提交版本，下载 BOSS 文件并调用 Native Resume。

MUST会话归属与单写者

所有读写由服务端鉴权；每 Session 同一时刻只有一个被授权的 Writer 提交 Checkpoint。

MUST明确持久化边界

一轮结束时落一次完整快照；成功提交后才标记为 durable。进行中途崩溃只恢复到最近成功版本。

范围：只负责 Session Continuity，不迁移运行中的进程、外部训练任务或已执行副作用。代码 Workspace、Magpie 仓库、模型服务凭证和 Taskbook 分别由其已有机制管理，恢复时重新挂载/加载。

不引入时序数据库。Session 原生状态是按身份和版本恢复的文件快照，不是按时间窗口聚合的指标数据。

02 · 最小架构

              Chat / @superagent
                 Session Manager
            owner · version · lease
                     |
          Runtime Adapter / Worker
         Pi · Claude Code · Codex
           |                 |
    Ephemeral HOME       restore / flush
     (runtime native)         |
           +----------+------+
                      |
           +----------+----------+
           |                     |
         MySQL                  BOSS
  user / session metadata   immutable .tar.zst
  lease / epoch             native files + manifest
  committed_version         versioned checkpoints
  object_key + sha256       retained last N versions

MySQL 负责当前哪个版本有效、谁可以写；BOSS 保存这个版本对应的真实文件。BOSS 不能替代 MySQL 的事务与权限判断，MySQL 也不再保存完整 LONGBLOB。

使用公司现有的 BOSS 服务和 SDK。不假设 BOSS 兼容 S3 API：先确认内部上传、下载、读取对象元数据及访问权限接口；平台只需要一个很薄的存取适配器。

interface SnapshotStore {
  put(key: string, bytes: Uint8Array): Promise<void>
  get(key: string): Promise<Uint8Array>
  head(key: string): Promise<{ size: number }>
  delete(key: string): Promise<void>  // 仅清理任务调用
}
现阶段不做：MinIO / 独立 S3、Kafka、Redis 缓存、增量快照引擎、通用 Blob 数据库。先复用 BOSS + MySQL，按真实快照大小决定是否需要增量化。

03 · 生命周期与数据流

新建 Session

  1. 鉴权并登记 SessionMySQL 保存 tenant_id / user_id、runtime、workspace_ref、harness_ref、native_session_id（创建后填写）和 committed_version=0。
  2. 获得 Writer LeaseMySQL 颁发 owner_epoch 和 lease_owner；一个 Session 仅由一个有效 Worker 修改。
  3. 正常运行原生 AgentWorker 准备独立的临时 HOME 与 Workspace，原生 Runtime 负责自己的 JSONL / SQLite 等文件。
  4. 轮次完成后生成 CheckpointAdapter 在一致性边界获取需要的原生文件，生成 manifest + 压缩包，上传 BOSS，校验可读后用 MySQL 事务提交新版本。

Worker A 故障后在 Worker B 恢复

  1. 验证用户与 Session 所有权后端按认证上下文查 MySQL，不信任客户端提交的 user_id。
  2. 接管 Lease确认旧进程已停止、隔离或失去执行资格，MySQL 增加 owner_epoch；旧 Writer 不能再提交新版本。
  3. 读取指针并下载用 committed_version 查 session_checkpoints 的 object_key，从 BOSS 下载 Snapshot 并校验 SHA-256；校验失败尝试上一有效版本。
  4. 在新 Worker 还原原生环境安全解压到指定 Cache 目录，准备对应的 Workspace、Harness 版本与用户权限，再调用 Runtime 原生 Resume。
  5. 后续执行继续产生新版本不改变平台 Session ID；恢复成功后下一轮执行仍通过 BOSS + MySQL 提交。

恢复承诺：只能恢复最后成功提交的原生 Session 状态。不保证恢复尚未完成的工具调用，也不能对外部系统操作提供 exactly-once 语义。

04 · MySQL 索引与 BOSS 对象

第一版仍然只需要两张 Session 专用表。Task、Run、Web 展示事件沿用工作台已有数据模型，不与 Runtime 原生文件混存。

MySQL · 概念性 Schema（字段可随现有库约束调整）
CREATE TABLE agent_sessions (
  id                VARCHAR(64) PRIMARY KEY,
  tenant_id         VARCHAR(64) NOT NULL,
  user_id           VARCHAR(64) NOT NULL,
  runtime           VARCHAR(32) NOT NULL,
  native_session_id VARCHAR(255),
  workspace_ref     VARCHAR(255),
  harness_ref       VARCHAR(255),
  committed_version BIGINT UNSIGNED NOT NULL DEFAULT 0,
  owner_epoch       BIGINT UNSIGNED NOT NULL DEFAULT 0,
  lease_owner       VARCHAR(128),
  lease_expires_at  DATETIME(6),
  status            VARCHAR(32) NOT NULL,
  updated_at        DATETIME(6) NOT NULL,
  KEY idx_owner (tenant_id, user_id, updated_at)
);

CREATE TABLE session_checkpoints (
  session_id    VARCHAR(64) NOT NULL,
  version       BIGINT UNSIGNED NOT NULL,
  owner_epoch   BIGINT UNSIGNED NOT NULL,
  object_key    VARCHAR(512) NOT NULL,
  sha256        CHAR(64) NOT NULL,
  size_bytes    BIGINT UNSIGNED NOT NULL,
  created_at    DATETIME(6) NOT NULL,
  PRIMARY KEY (session_id, version)
);

agent_sessions.committed_version 与 session_checkpoints 新行在同一 MySQL 事务中提交。该版本对应的 BOSS 对象必须已经完整上传并验证可读。对象 Key 不允许覆盖写。

BOSS · 逻辑路径示例（私有 Bucket）
harness/sessions/{tenant-id}/{session-id}/
  checkpoints/
    v000001-{opaque-id}.tar.zst
    v000002-{opaque-id}.tar.zst
    v000003-{opaque-id}.tar.zst

一个 Snapshot 包只包含 Adapter 确认恢复确实需要的原生文件，以及 manifest.json（schemaVersion、runtime、runtimeVersion、nativeSessionId、harnessRef、相对文件路径、校验摘要）。不要直接打包整个 HOME。

敏感数据边界：Session Transcript 可能包含用户输入、内部代码或工具返回的敏感内容；即使剔除 credential 文件，也应将整包当作敏感数据。BOSS Bucket 必须私有，使用受控服务账号、必要的加密与访问审计；Runtime 凭证重新授权/注入，不能靠恢复包分发。

05 · Runtime Adapter：只负责原生 Session

RuntimeSnapshot 内容恢复方式需要实测的边界
PiJSONL Session、分支与会话元数据原生打开指定 Session路径、分支、文件清单与 Skills/工作目录恢复
Claude CodeTranscript 和恢复所需原生元数据Runtime 原生 Session ResumeCWD 与项目路径绑定、原生文件布局、版本兼容性
CodexThread Rollout 及必要索引/元数据App Server thread/resume新版本可能有 SQLite / 分页事件；必须用原生机制确认一致性
interface NativeSessionAdapter {
  start(context): Promise<NativeSession>
  checkpoint(context): Promise<ConsistentSnapshot>
  restore(context, snapshot): Promise<NativeSession>
  resume(context): Promise<void>
}

一致性边界：完成一个 Agent Turn、工具执行静止后才生成完整快照。若 Runtime 使用 SQLite，需要安全备份 API 或等效冻结机制；不能直接复制仍在写入的数据库。不同 Runtime 的原生文件集必须单独验证，不硬编码公共路径。

Codex 的 App Server 文档明确提供持久 Thread 和 thread/resume；注意这不等于原生 Session 文件可以直接跨机器无损搬运，仍需验证 Adapter 提取与恢复的文件集合。

06 · 用户隔离与执行权限

MySQL: authenticated (tenant_id, user_id) → session_id
BOSS : private bucket; object keys only from DB references
Worker A: isolated HOME/session-{id} [temporary]
Worker B: restore from verified BOSS snapshot
  • 平台隔离：读取、续聊、Checkpoint 和删除均经后端按真实 tenant_id / user_id 验证；不直接向客户端提供可绕过权限的 BOSS 地址。
  • 执行隔离：同一个 Linux UID 启动多个用户的任意 Shell 命令并不能实现用户隔离。首期若仅内部单用户可简化；开放多用户执行前至少实施独立 UID / Workspace 与可信 Runner Broker，或等效更强的隔离。
  • 凭证隔离：Token / Key 不属于 Session Snapshot；用户认证与工具授权来自专门的用户配置与 Secret 管理，启动时注入。对历史 Transcript 仍按敏感内容处理。
  • 归档清理：优先保留最近 3 个成功提交的 Checkpoint，过期对象以 DB 指针和保留策略为准异步删除，不能删除活跃版本。

07 · Checkpoint 提交协议与故障处理

建议首期采用每个完成的 Turn 一个持久版本：允许 Web 流式显示执行过程，但只有 BOSS 上传 + MySQL 提交成功，才将此轮状态标为 durable。持久化失败时应显示待同步状态，不能宣称已经可跨机器恢复。

Flush / Commit：固定 5 步

  1. 进入安全边界并生成 SnapshotAdapter 获取一致的原生文件集合，建立 Manifest，压缩并计算 SHA-256；记录提交前的 base_version 和 owner_epoch。
  2. 上传 BOSS 不可变 Object使用新对象 Key，上传后验证对象可读且文件摘要正确；不能把多段上传的 ETag 直接当作 SHA-256。
  3. MySQL 短事务验证所有权锁定 Session，检查用户、lease_owner、owner_epoch、租约有效期，以及 committed_version==base_version。
  4. 同事务提交 Checkpoint + 指针INSERT session_checkpoints(version=base+1)，UPDATE agent_sessions.committed_version，然后 COMMIT；旧 Worker 提交不满足 epoch 条件必须拒绝。
  5. 标记 durable 并允许继续提交成功才清理本地 dirty；Worker 可以继续下一轮，失败保留上次指针和本地待上传状态。
故障点系统表现与恢复
BOSS 上传失败MySQL 不变；本轮标记未持久化，重试上传。
BOSS 成功但 MySQL 失败产生孤儿对象；旧 committed_version 仍有效，按保留期清理孤儿对象。
MySQL 成功但 Worker 崩溃新 Worker 可按新指针下载 BOSS 并恢复，无需旧 Worker 本地文件。
最新对象损坏或无法读取检测 checksum / 下载失败；尝试上一个有效 Checkpoint，并明确报告回退版本。
旧 Worker 在 Lease 转移后提交MySQL owner_epoch / base_version 校验失败；无法覆盖新版本。

重要限制：Lease 只能阻止失效 Worker 提交 Session 状态，不能天然阻止它继续执行外部命令；跨机器接管前需要终止或隔离原进程。训练提交、部署等副作用另外使用权限关口和幂等键，不由 Session Persistence 承诺 exactly-once。

08 · 验收与实施顺序

实验操作通过标准
Magpie Chat 首个 Runtime（首个必过）选择已在 Magpie Chat 中可用的一个 Runtime（Pi / Codex / Claude Code），Worker A 多轮工具调用后提交 BOSS + MySQL；删除本地 HOME，再由 Worker B 恢复原生 Session 可继续；历史、工具上下文、Harness 环境可用，无需 Worker A 本地文件
其余 Runtime为未覆盖的 Runtime 分别做多轮 Session 跨机迁移与 Resume各 Runtime 原生 Resume，未发生会话串线或上下文丢失
上传/数据库故障注入 BOSS 上传失败、MySQL 事务失败与对象损坏不会推进到无效版本；有明确未持久化状态；必要时回退最近有效版本
并发与用户隔离旧 Worker 持有过期 Lease 提交；其他用户尝试按 ID 恢复过期写入和越权访问全部拒绝
成本与可靠性采样 Snapshot 大小（P50/P95/P99）、上传时延、BOSS 请求量和恢复耗时能判断是否继续采用全量 Snapshot，或针对大 Session 再做增量优化

最短落地路线

① 确认公司 BOSS Bucket / SDK / 权限 → ② 建 MySQL 两表 + BOSS SnapshotStore → ③ 先跑通 Magpie Chat 目前可用的一个 Runtime 的真实 Checkpoint/Restore → ④ 补其余 Runtime → ⑤ 做跨 Worker、故障和用户隔离测试。

依旧坚持产品主线：P0 是 Magpie Chat。Session Persistence 是它的恢复能力，不应演变成单独的存储平台项目。

验收终点：清空 Worker A 的全部本地 Session 后，仅凭 MySQL 已提交指针、BOSS Snapshot 和独立配置，Worker B 能继续同一个原生 Session。

本页为设计方案，尚未验证 BOSS 的 S3 API 兼容性、具体 SDK、对象一致性语义或跨 Worker 的真实 Runtime Resume；实施前按内部文档与实测核对。
