Multi-tenant Agent Session Persistence

MySQL 是唯一的 Session 持久化事实源；Server 本地状态只是可重建的临时 Cache。 支持 Pi / Claude Code / Codex 的原生 Session，按用户隔离、异步落库、跨机器恢复。允许故障时丢失尚未同步的少量最近状态。

01 · 目标与非目标

MUSTSession 跨机器恢复

任意新 Worker 仅凭 MySQL 中的已提交 Session 状态和用户授权即可重建本地运行缓存。

MUST多用户隔离

用户不能读取或恢复别人的 Session、Runtime Home、工作空间或身份凭证。

TRADE-OFF允许少量近期状态丢失

先采用异步写回；同步频率与持久化等级留作后续演进。

范围：本页解决 Session Continuity（会话状态持续性），不承诺 Execution Continuity（中断中的工具调用自动继续）。代码 Workspace、Secrets、训练/部署副作用属于独立的持久化与恢复问题。

02 · 最小架构

                  Web Chat / SuperAgent
                  user auth · session routing
                              |
                      Session Manager
           ownership · version · active writer
                              |
                 Runtime Adapter interface
                      /       |       \
                     Pi    Claude     Codex
                              |
              +---------------+---------------+
              |                               |
    Worker A / B / N                        MySQL
  isolated Runtime process           authoritative Session DB
  temporary native files   <------>   metadata + native state
  dirty tracking & flush              committed version
  (rebuildable cache)                  user ownership

Worker 执行期间，Runtime 仍使用自己熟悉的本地文件；Session Manager 在 Cache Miss 时从 MySQL 装载，在更新后异步 Flush。其他机器无需共享文件系统、远程 Volume 或 MinIO。

写入所有权：同一个 Session 只允许一个有效 Writer。MySQL 负责判断谁有资格提交更新；旧 Worker 不能用过期版本覆盖新机器的提交。

03 · 生命周期与数据流

新建 Session

  1. 服务端鉴权并生成 Session IDMySQL 写入 user_id、runtime、初始状态和 owner epoch。
  2. 创建隔离的本地 Cache为这个 Session 准备固定的 HOME、Runtime 数据目录和 Workspace 入口。
  3. 调用原生 Runtime通过 Adapter 创建 Pi / Claude Code / Codex Session，持久化原生 Session ID。
  4. 异步同步到 MySQLRuntime 文件发生变化时标记 dirty，在安全写入点生成状态包并提交。

恢复到另一台 Server

  1. 验证请求用户的 Session 所有权由服务端鉴权结果绑定 user_id，而非信任请求中的 user_id。
  2. 取得当前写入权通过 MySQL Lease / owner epoch 阻止同一 Session 在两台 Worker 并发执行。
  3. 下载最后已提交的原生状态解压到新 Worker 的本地临时目录，保留容器内部约定的固定绝对路径。
  4. 恢复 Runtime 环境与 Native Session注入用户配置和授权，调用 Pi / Claude Code / Codex 原生 Resume。
  5. 继续交互并回写 MySQL新的执行进度从新 Worker 的 Cache 异步同步，Session ID 不变。

04 · MySQL 持久化模型

第一版用两张核心表即可表达会话归属和不可变状态版本。以下 SQL 为概念性建模，生产实现需再确定索引、清理策略、事务大小和恢复窗口。

Schema sketch
CREATE TABLE agent_sessions (
  id                VARCHAR(64) PRIMARY KEY,
  user_id           VARCHAR(64) NOT NULL,
  runtime           VARCHAR(32) NOT NULL,
  native_session_id VARCHAR(255),
  committed_version BIGINT NOT NULL DEFAULT 0,
  owner_epoch       BIGINT NOT NULL DEFAULT 0,
  lease_owner       VARCHAR(128),
  lease_expires_at  DATETIME(6),
  status            VARCHAR(32) NOT NULL,
  updated_at        DATETIME(6) NOT NULL,
  KEY idx_user (user_id, updated_at)
);

CREATE TABLE session_states (
  session_id    VARCHAR(64) NOT NULL,
  version       BIGINT NOT NULL,
  owner_epoch   BIGINT NOT NULL,
  state_blob    LONGBLOB NOT NULL,
  checksum      CHAR(64) NOT NULL,
  created_at    DATETIME(6) NOT NULL,
  PRIMARY KEY (session_id, version)
);

state_blob 是包含原生文件及 manifest 的压缩状态包，而不是统一消息格式；可以含多个文件及子目录。committed_version 只指向已经完整写入且通过校验的版本，必须在一个 MySQL 事务中提交。

大状态包会增加 MySQL 读写、复制与备份成本；第一版需测量典型、P99 Session 大小与写入量，并检查 max_allowed_packet 等限制。增量状态、保留版本数及分块存储属于后续优化。

05 · 三种 Runtime 的 Adapter

Runtime需要保存的原生会话状态恢复方式注意事项
PiSession JSONL / 会话树及元信息从还原的 Session 路径打开维护 Session 目录和固定工作路径；用户 Skills / Secrets 不作为 Session Blob 一起保存
Claude Code项目下 Transcript / Session 元数据和 Resume 所需配置使用原生 --resume项目目录编码依赖 CWD；仅同步 Transcript 可能不够，需用真实 Session 测试验证状态包边界
CodexSession JSONL、Resume 所需的状态索引及元数据使用原生 resume可能涉及 SQLite、路径和索引；需一致性复制，不应直接读取正在写入的数据库文件

最小 Adapter 合同

interface SessionAdapter {
  create(localHome, workspace): NativeSession
  resume(localHome, workspace, nativeSessionId): Runtime
  checkpoint(localHome): ConsistentNativeState
  restore(localHome, nativeState): void
}

Checkpoint 实现边界：每轮结束 / Runtime 空闲时生成一致的本地状态视图。长任务执行中不能简单复制正在写入的文件；Codex SQLite 必须采用安全备份或在无写入边界复制。三种 Runtime 的具体文件集应由 Adapter 实测决定，避免硬编码整个用户 Home。

06 · 多租户隔离

MySQL
  user_id → session_id → committed native state

Worker (ephemeral)
  /runtime/session-001/home/       # 独立可写 Runtime Home
  /runtime/session-001/workspace/  # 独立本地工作副本
  /runtime/session-002/home/       # 另一个 Session
  • 访问隔离：Session Manager 在所有读取、创建、恢复与写回路径执行 user_id ownership 检查；用户 ID 必须来自可信认证上下文。
  • 执行隔离：不同用户运行在独立容器或具有等效安全边界的环境中。相同用户的不同 Session 也建议独立 Runtime 可写目录，避免共用 SQLite / Transcript 写入。
  • 凭证隔离：Secret Store / 用户级授权与 Session Blob 分离，启动时按身份注入；不要把 OAuth token、API Key 等写入 MySQL Session 状态包。
  • 状态隔离：以 session_id 对应一个单写者；机器复用不代表目录复用。所有 Cache 目录均可丢弃并从 MySQL 重建。

07 · 异步持久化与一致性

V1Write-behind

本地写入后标记 dirty，按会话轮次结束或定时触发 Flush；不承诺每个 Token / 工具事件强持久。

RECOVERYLast committed

故障恢复只从 MySQL 已提交版本启动。未同步的最新一小段状态允许丢失。

FUTUREDurability levels

再根据实际需求演进：Best Effort、Turn Durable、关键步骤同步提交。

Flush 协议（最小正确性）

  1. 生成一致的 Native Snapshot在 Session 写入安全边界读取文件和必要索引，计算 checksum；不阻塞其他 Session。
  2. 提交到 MySQL使用短事务锁定目标 Session，检查 owner epoch 和期望版本。
  3. 写入新状态并推进指针同一事务 INSERT 新的 session_states，UPDATE agent_sessions.committed_version。
  4. 仅在事务成功后清除 Dirty失败则保留本地 dirty、重试或由故障恢复接受丢失窗口；过期 Writer 提交必须被拒绝。

重要限制：Lease / epoch 主要保护 MySQL 中的提交与所有权，不会自动阻止已失去 Lease 的旧进程向外部系统发起操作。需要先确保旧 Worker 停止或隔离；部署、训练提交等有副作用动作由独立 Execution 层核对。

08 · 最小验收实验

实验操作通过条件
跨机器恢复Server A 各创建 Pi / Claude Code / Codex Session，正常 Flush 后关闭 A；Server B 清空本地 Cache，从 MySQL 恢复三个 Runtime 都能 Native Resume；历史对话可追溯；后续交互正常
故障丢失窗口本地新增消息后、尚未 Flush 时杀掉 A恢复到 MySQL 最新已提交版本；丢失窗口被明确记录，不误报为完整恢复
用户隔离用户 B 用用户 A 的 Session ID 发起读取、Resume、写回全部拒绝，不能拿到 A 的状态包或凭证
并发冲突A 保留旧 Lease，B 接管并成功提交后，A 尝试回写A 的旧 epoch 不能覆盖 B 的版本
双 Session 并发同用户并行运行两个 Codex / Claude Session，分别 Flush各自恢复正确，无写入互扰或状态交叉

首版交付顺序

① MySQL 状态模型与 Session Manager → ② Pi Adapter 端到端 → ③ Claude Code / Codex Adapter → ④ 用户隔离与跨机故障验收。 优先证明恢复正确，再优化增量写入和高级持久化策略。

目标结果：清除任何 Worker 的本地 Cache 后，已提交 Session 仍可在另一台 Server 继续。

本页为方案设计，不代表已部署运行。非目标：原始进程迁移、进行中的工具动作重放、Workspace 自动持久化、Exactly-once 外部操作。
