# L01 · 一份 Eval 报告究竟证明了什么？

本单元是可跳过的参考材料。项目目标和进度以同目录 `project.json` 为准。已经能准确区分测试、行为和收益时，直接进入实验设计。

## 只保留一个判断问题

面对“改动后测试全通过，Agent 更可靠，而且没有性能退化”的报告，分别检查它测了什么，以及这些证据能支持到哪一层。

测量器单测验证其覆盖的输入与断言，不等于同样次数的真实 Agent 成功。真实任务的终态支持已观察任务的结论；缺失轨迹时，不能声称已经证明所有中间机制。实际收益还需要对应任务的质量、人工介入、返工和端到端代价。

这里复用已有历史案例的学习问题，不把历史报告写成当前环境状态，也没有新增模型运行。

## 一个明确的汇总反例

以下是人为构造的数字，不是生产指标或真实 Agent 试验结果。每项重复三次。

| Case | Base 延迟 | Candidate 延迟 |
| --- | ---: | ---: |
| case-0 | 100 | 250 |
| case-1 | 100 | 50 |
| case-2 | 100 | 50 |
| case-3 | 100 | 50 |
| case-4 | 100 | 50 |

整体中位数从 100 降到 50；整体平均数从 100 降到 90；case-0 延迟却上升 150%。三种描述可以同时成立。

问题不是中位数“无用”，而是目标量与接受条件是否一致。要求总体中位数下降，与要求重要 case 不退化，属于不同判断。仅换成平均数也不能自动解决这个问题。

重复次数不等于新任务数。这组构造数字没有实际抽样过程，不应将其置信区间解释为真实模型收益。

## 向实际比较推进

候选题：一条规范从直接注入改为按需读取后，指定任务的约束保持是否变化？

保持规范内容、宿主、模型和其他配置不变。先写清准备支持哪个决定，再设计任务覆盖、终态判据、加载观察、失败记录和分析方式。不要同时修好规范内容，再把收益归因于加载方式。

个人需要留下：自己的预测、一个替代解释，以及什么结果会改变判断。Agent 可以准备材料和脚本，但不能代答后标记个人已掌握。
