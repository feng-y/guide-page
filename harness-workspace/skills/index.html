ROOK · SKILL MANAGEMENT · v0.2 · 2026-11-17

Skill 管理：系统 + 个人，两级足够

镜像提供初始 Skill，管理员全权维护系统 Skill；用户管理个人 Skill，且只能在自己的运行环境里使用。Rook 负责确定装载清单，不重新实现 Skill 协议或 Agent Loop。

2 个范围管理员可升级/删除镜像 Skill用户私有隔离原生 Runtime 加载Magpie Chat 优先

一、合理性评估与必要修正

两级管理方向正确。 原方案不需要第三层 Built-in，也不需要 Release Registry。但如果原样实现，镜像扫描和用户执行隔离会出现实际问题，下面三处需要明确。

事项结论具体规则
系统 / 个人两级保留系统 Skill 只由管理员管理（包含镜像内置与管理员新增）；用户只能管理自己的 Skill。
镜像内置 Skill修正镜像 Skill 只是初始化来源，不直接暴露给 Runtime 自动扫描。首次初始化后，以持久化的系统清单为准；管理员停用/删除不因重启或换镜像而失效。
修改与已有 Session修正每次保存 Skill 内容生成不可变文件标识；Session 记住装载时的内容标识。正在执行不热切换；旧 Session 恢复仍可使用原内容。
用户 Skill 隔离修正不只是 UI 权限隔离。读取和装载按用户身份检查，Agent 执行时使用隔离的 HOME / OS 执行身份；没有执行隔离前，不向不同用户开放任意脚本 Skill。
Git / ZIP 来源保留简化支持手动导入和手动更新，使用固定 Git commit 或上传文件；不做自动订阅更新和审批平台。
Skill 格式复用使用 Agent Skills 标准的完整目录结构（SKILL.md、scripts、references、assets）。

二、装载流程：Rook 唯一负责实际可见集合

系统 Skills镜像初始 + 管理员维护
用户 Skills本人上传 / 从 Git 添加
↓
Rook 解析当前用户可用的 Skills系统清单 + 当前用户清单 · 唯一名称 · 启用状态
↓
生成 Session Skill 清单，并在用户专属执行目录装载固定内容摘要 · 只读拷贝 / 受控挂载 · 不共享用户 HOME
↓
Codex / Pi / Claude Code使用各自原生 Skill 发现机制
SuperAgent（后续）沿用已确定的 Skill 清单
最重要的技术约束：镜像内置 Skill 应放在 /opt/rook/seed-skills/ 这样的非扫描目录；管理员禁用后，不能仍被 Runtime 从 /etc/codex/skills、共享 HOME 或其他默认路径偷偷加载。Rook 只把有效清单复制到当前用户的 Runtime Skill 目录。项目仓库自身带的 Skills 属于 Runtime 的项目上下文，需另外识别冲突，首期不接管其生命周期。

三、管理行为只保留基本操作

ADMIN

系统 Skills

列出所有系统 Skill，包含来自镜像的默认 Skill。可添加、更新、停用、删除；删除镜像默认 Skill 后，后续部署不能自动复活它。

USER

我的 Skills

仅显示自己的 Skill。可以添加、更新、停用、删除；不能更改系统 Skill。与系统 Skill 同名时拒绝安装，避免隐式覆盖。

新版本只影响新 Session；已有 Session 默认保持之前装载的内容。需要让旧 Session 使用新 Skill 时，由用户明确刷新并在下一轮安全边界应用，而不是无提示热更新。

镜像升级：已有环境不重复初始化 Skill；新增镜像默认 Skill 由管理员明确选择导入。管理员配置是权威状态，镜像不能自动覆盖。仅当首次初始化系统清单为空时才导入镜像默认值。

四、存储：复用 BOSS + MySQL

位置保存内容
镜像默认 Skill 文件，仅供首次初始化与管理员手动导入
MySQLSkill 名称、归属范围（system / user）、用户 ID、启停状态、当前内容摘要和来源
BOSS不可变的 Skill 文件包（按内容摘要保存，旧 Session 需要的旧包保留）
Session 状态实际装载的 Skill 名称及文件包摘要，便于跨 Worker 恢复
Worker 临时目录本次 Session 的已解析 Skill 文件，重新启动即可重建
Skill record（逻辑模型）
  namespace     = "system" | "user:{userId}"
  name          = "northstar"  // namespace 内唯一
  enabled       = true
  active_hash   = sha256(whole-skill-package)
  source        = image | git | upload

Session
  skill_manifest = [{ namespace, name, hash }, ...]

不需要独立 Release 表、Skill Registry 或发布状态机。每次管理员或用户修改内容时，先将完整包保存到 BOSS，再更新 MySQL 的当前摘要；旧内容在仍被 Session 引用时不清理。BOSS Key 不直接暴露给其他用户。

五、实施顺序与完成标准

P0

先贯通 Magpie Chat

镜像/管理员提供的系统 Skill 可被真实 Codex、Pi 或 Claude Code 原生发现；Magpie 是模型工程领域 Harness，不把整个 Magpie 错误地压成一个 Skill。

P1

管理员管理系统 Skill

无需重建镜像，添加/更新/停用系统 Skill；镜像升级和 Worker 重启后生效状态保持一致。

P2

用户私有 Skill 与跨 Worker 恢复

A 只能看到和装载自己的 Skill；A 的脚本不能读取 B 的目录；升级后新 Session 使用新版本，已有 Session 仍能按旧摘要从 BOSS 恢复。

最小验证：系统原有 review，管理员停用后，新 Session 的三个 Runtime 均不再发现它；管理员升级后原 Session 仍能恢复原版本；用户 A 添加 helper，用户 B 既不能读取也不能通过 Agent Shell 访问它。

六、相关依据与边界

遵循 Agent Skills 规范；Codex 官方 Skill 加载路径文档说明 Runtime 会扫描多个位置，且同名 Skill 不一定自动合并，因此 Rook 必须控制实际扫描集合，不依赖 Runtime 发现顺序。

项目资产：feng-y/skill 的 Skills 有各自职责与项目规则；Magpie 是模型工程领域 Harness，除了 Skills 还可能包含规则、Context 与内部工具配置。这些应由各自原有机制提供，不属于 Rook 的“Skill 管理”范畴。
